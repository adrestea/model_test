## 三、依 A76 示例 · 待真机/TRM 复核(原始 PMU 编号与 TMA 公式)

> 仅适用 Cortex-A76;他核(A78/A710/A715/X1/X2 等)需查对应 TRM/PMU guide。

- [~] **§6.1.1 A76 事件编号表**:`r03`(L1D_CACHE_REFILL)/`r04`(L1D_CACHE)/`r05`(L1D_TLB_REFILL)/`r17`(L2D_CACHE_REFILL)/`r22`(BR_MIS_PRED_RETIRED)/`r23`(STALL_FRONTEND)/`r24`(STALL_BACKEND)/`r28`(MEM_ACCESS_CHECKED)——**半验(2026-08-04)**。通过 ARM 架构参考(CMSIS-Core ARMv8.1-M PMU 事件定义)对照：r03=0x03(L1D_CACHE_REFILL ✅)、r04=0x04(L1D_CACHE ✅)、r05=0x05(L1D_TLB_REFILL ✅ ARMv8-A)、r17=0x17(L2D_CACHE_REFILL ✅)、r22=0x22(BR_MIS_PRED_RETIRED ✅)、r23=0x23(STALL_FRONTEND ✅)、r24=0x24(STALL_BACKEND ✅)。**⚠️ r28=0x28 在标准架构中为 L2I_CACHE_REFILL，非 MEM_ACCESS_CHECKED**——MEM_ACCESS_CHECKED 可能为 A76 实现特有定义(A76 TRM 需核实)或编号错误。**r04(裸 r04)未标注事件名**——补充为 L1D_CACHE。
- [~] **TMA L1 公式系数**:`pipeline_width = 4`(A76 4-wide)——**✅ 半验(2026-08-04)**:A76 是 4-wide 解码(公开资料确认)。`penalty ≈ 11 cycles`——**待核实**:此为 A76 分支误预测惩罚经验值,需对照 A76 TRM 确认。A78/A710/X1 等需另查对应 TRM。
- [ ] **核识别**:读 `/sys/devices/system/cpu/cpu*/regs/identification/midr_el1` 确认目标 SoC 实际核型号,据此选 TRM。
- [ ] **STALL_FRONTEND/BACKEND 语义**:ARM imp-def,各核实现略异;A76 公式照搬到非 A76 会出错。
- [ ] **TMA L2 细分阈值**(全程 §6.1b):Backend Memory <20% / Core <15% 等——需配合 A76 stall 事件,他核不通。

### ✅ 实测修正(已回填到精通线/路线图)

- **C1 `frame_timeline_event` 在 v57.2 不存在**(`sqlite_schema` 计数=0)。本线原「Lv0/Lv1 起手用 `frame_timeline_event` 对齐 M0d #2」在该版本跑不通;M0d #2 SQL(`FROM frame_timeline_event e ... e.actual_ts ... e.display_frame_token = s.arg_set_id`)同样过时。**修正方向**:Lv0/Lv1/Lv2/Lv3 统一用 `actual_frame_timeline_slice`(列用 `ts`/`dur`,非 `actual_ts`);`frame_timeline_event` 可能仅存于其他/旧版本,执行前以 `SELECT count(*) FROM sqlite_schema WHERE name='frame_timeline_event'` 探测。
- **C2 `jank_type` 是描述性字符串,非 `Self/App/SF/Display` 枚举**。真实值:`App Deadline Missed` / `SurfaceFlinger CPU Deadline Missed` / `SurfaceFlinger GPU Deadline Missed` / `SurfaceFlinger Scheduling` / `Display HAL` / `Buffer Stuffing` / `Prediction Error` / `Unknown Jank` / `None`,且有逗号组合(如 `"SurfaceFlinger CPU Deadline Missed, App Deadline Missed"`)。**修正方向**:所有 `jank_type='App'`/`='Self'` 改 `LIKE '%App Deadline Missed%'`(或按真实枚举);术语/路线图「四分类 Self/App/SF/Display」是底层 `FrameJankType` bitmask 的高层映射,需补真实枚举对照表(App Deadline Missed→App 段;SF * Deadline/Scheduling→SF 段;Display HAL→Display 段;Buffer Stuffing/Prediction Error/Unknown→其他)。
- **C3 Android App 主线程名不是 `'main'`**(task comm 15 字符截断,如 `com.google.android.apps.nexuslauncher` 主线程名为 `s.nexuslauncher`,utid 736/tid 2782)。**修正方向**:`WHERE name='main'` 在 Android App 上命中 0 行;改用 `tid=pid`(主线程 tid==进程 pid)、或匹配截断进程名、或 `SELECT utid FROM thread WHERE upid=<app> ORDER BY tid LIMIT 1`(tid 最小者通常即主线程)。
- **C4a binder EXTRACT_ARG 的 arg key 名不对**(**已回填**):真实 key 是 **`'data size'`**(带空格),非 `'data_size'`(下划线);**无 `'reply_size'`** key(有 `'reply transaction?'` 布尔)。另含 `'calling tid'`/`'destination process'`/`'destination thread'`/`'destination node'`/`'code'`/`'flags'`/`'offsets size'`/`'transaction id'`。**已落实**:精通线/路线图 `EXTRACT_ARG(arg_set_id,'data_size')` → `'data size'`;`'reply_size'` 删除,改 `'reply transaction?'`/在 reply slice 上读 `'data size'`;EXTRACT_ARG 专题与差异表脚注补 binder arg key 全集。
- **C4b Binder 对端关联首选 EXTRACT_ARG,非 name 匹配 JOIN**(**已回填**):实测 `EXTRACT_ARG(arg_set_id,'destination process')` 直接给服务端 pid(V11:dest 712/1782/714)。**已落实**:Lv2 Binder 对端 SQL 主写法改为 `EXTRACT_ARG(client.arg_set_id,'destination process')` JOIN process 拿服务端;R4 的 name+dur+utid 修补降为「无 arg 时的备用」(精通线尾节疑点③ + 差异表 Binder 行脚注 + 路线图练习 2.2)。
- **C5 `android_jank_cuj` 依赖 CUJ 标记,V12 实测非 CUJ trace 输出空**(**已回填**):`--run-metrics android_jank_cuj` 在无 CUJ 交互标记的 trace 上返回 `{}`。**已落实**:精通线 Lv3 `my_jank_summary` 主写法改为 P95/帧统计**直接基于 `actual_frame_timeline_slice`**(按 upid/layer_name 分组),不强制 CUJ;`RUN_METRIC('android/android_jank_cuj.sql')` 降为「可选 CUJ 分组(需 CUJ 交互标记的 trace)」(§2.2.3 注 + Lv3 步骤 5 + 差异表 + 路线图练习 3.3)。

> 这些修正确证了「列名待核 / 以 `.schema` 校对」警示的必要性;真 trace 实测比纯解析更能暴露版本差异。C1-C3、C4-C5 均已回填到 `tools-perfetto-simpleperf-精通.md` 与 `perfetto-simpleperf-练习路线图.md`。

#### 3.3 PMU 事件编号 ✅ 半核

通过 ARM CMSIS-Core ARMv8.1-M PMU 事件定义(来源:arm-software.github.io/CMSIS_5)对照 ARMv8-A PMUv3 架构标准:

| 编号 | 清单事件名 | 架构标准 | 判定 |
|------|----------|---------|------|
| r03 (0x03) | L1D_CACHE_REFILL | `ARM_PMU_L1D_CACHE_REFILL` = 0x0003 | ✅ 匹配 |
| r04 (0x04) | (裸 r04,未注事件名) | `ARM_PMU_L1D_CACHE` = 0x0004 | ✅ L1D_CACHE |
| r05 (0x05) | L1D_TLB_REFILL | ARMv8-A 架构事件 0x05(L1D_TLB_REFILL) | ✅ 匹配 |
| r17 (0x17) | L2D_CACHE_REFILL | `ARM_PMU_L2D_CACHE_REFILL` = 0x0017 | ✅ 匹配 |
| r22 (0x22) | BR_MIS_PRED_RETIRED | `ARM_PMU_BR_MIS_PRED_RETIRED` = 0x0022 | ✅ 匹配 |
| r23 (0x23) | STALL_FRONTEND | `ARM_PMU_STALL_FRONTEND` = 0x0023 | ✅ 匹配 |
| r24 (0x24) | STALL_BACKEND | `ARM_PMU_STALL_BACKEND` = 0x0024 | ✅ 匹配 |
| r28 (0x28) | MEM_ACCESS_CHECKED | `ARM_PMU_L2I_CACHE_REFILL` = 0x0028 | ⚠️ 不匹配 |

**关于 r28/MEM_ACCESS_CHECKED**:标准架构事件 0x28 = L2I_CACHE_REFILL。MEM_ACCESS_CHECKED 可能是:
1. A76 实现特有事件(需对照 A76 TRM DDIxxxx 确认)——某些核在 0x00-0x3F 范围内有实现特有重定义
2. 清单编号错误——可能是 0x13(MEM_ACCESS)的笔误,或 0x40+(A76 实现特有区间的其他事件)

**TMA 公式参数**:`pipeline_width=4`(A76 4-wide decode ✅ 公开资料确认),`penalty≈11`(需 TRM)。

**未覆盖**:A76 TRM 需 ARM 开发者账号访问,此次未能直接获取;但 7/8 个事件号通过架构标准交叉验证正确。
